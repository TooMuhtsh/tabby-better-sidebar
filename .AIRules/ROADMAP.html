Phase 1 — priorité absolue

Les deux fonctionnalités qui justifient de remplacer MobaXterm par Tabby + ce plugin.

SFTP contextuel

Bascule Profils/SFTP dans l'espace de la sidebar elle-même (pas un panneau séparé ancré à droite, façon FileZilla — plan initial abandonné). Volet fichiers locaux masqué par défaut. Déclenché depuis un onglet SSH déjà connecté (pas de session headless dédiée). SFTPPanelComponent/SFTPSession/SFTPFile confirmés exportés par tabby-ssh — pas de réimplémentation locale nécessaire, contrairement à profile-tree en son temps.

  • Focus multi-split : la vue se rafraîchit au clic sur un terminal différent au sein d'un même onglet scindé (liée au SplitTabComponent actif). Option de geler la vue active pour éviter des rafraîchissements accidentels pendant une navigation SFTP en cours.
  • Sensibilité au contexte : la vue reflète l'onglet SSH actif, bascule automatique si on change d'onglet ; état "en attente d'une session SSH active" (vue grisée ou retour sur la vue Profils) si l'onglet actif n'en a pas.
  • Persistance de navigation : dernier chemin distant visité mémorisé par onglet (en mémoire, pas persisté dans config.yaml).
  • Performances : liste de fichiers chargée par blocs (lazy loading RxJS au fil du défilement) pour éviter de figer le thread Electron sur un dossier distant très peuplé.
  • Suivi des transferts : flèches discrètes d'activité (↑ upload / ↓ download) à côté du profil concerné, pas de barre de progression classique (coût de re-render Angular trop élevé avec plusieurs transferts en parallèle). Pourcentage précis affiché uniquement au survol (tooltip). Mini-gestionnaire pliable en bas de sidebar pour l'historique/la file d'attente.

À vérifier au moment de l'implémentation : mécanique exacte du bouton de bascule (état par onglet ou global ?).

Workspaces

Plusieurs espaces de travail nommés (ex. perso / pro / projet X) filtrant la visibilité des groupes/profils affichés. Pas de mécanisme de masquage séparé : masquer un profil/groupe = le décocher du workspace actif — les workspaces SONT le mécanisme de masquage. Traité avant le SFTP (initialement prévu après) — choix explicite de l'utilisateur le 2026-07-28, ordre inversé par rapport à la priorisation d'origine.

Fait — testé et validé par l'utilisateur le 2026-07-29

Passe de test manuel complète dans Tabby (onglets de workspace, masquage et panneau de restauration, comportement de la barre de filtre, favoris cloisonnés, ordre cloisonné, imbrication depuis un workspace, survie à un redémarrage complet). Cinq correctifs livrés à cette occasion, voir AI-HISTORY (2026-07-29) et les pièges #30/#31. Commit 4f2fb59. Restent différés et non implémentés : icône par workspace, sélecteur adaptatif, couleurs contextuelles, export/import JSON — détaillés ci-dessous.

  • Stockage dans config.yaml via ConfigProvider, nouvelle clé sidebarPlus.workspaces: SidebarWorkspace[] (déclarée dans les defaults, piège #16). Pas de fichiers JSON externes séparés — option envisagée puis abandonnée, voir raisonnement de portabilité ci-dessous (inchangé). Export/import JSON ponctuel toujours prévu mais différé (non implémenté dans cette première passe).
  • Membership = listes d'exclusion, pas d'inclusion : chaque SidebarWorkspace porte hiddenProfileIds/hiddenGroupIds, pas une liste de membres. Décision actée pour que tout profil/groupe créé après coup reste visible par défaut dans tous les workspaces existants (cohérent avec le "masquer = décocher" du paragraphe d'intro) ; le workspace virtuel "Tous" est exactement le cas zéro-exclusion, jamais stocké en tant qu'entrée à part.
  • Masquage d'un groupe = cascade sur ses descendants pour l'affichage (calculé à la volée dans computeWorkspaceFilterState(), pas stocké) — sans ça buildGroupTree() fait disparaître silencieusement les sous-groupes orphelins d'un parent masqué au lieu de les remonter.
  • UX de masquage revue le 2026-07-28 (retour utilisateur après un premier essai du popup à cases à cocher multi-workspaces) : remplacée par une action en un clic, "Cacher dans le workspace" dans le menu contextuel Profil/Groupe — cible toujours le workspace actif, aucune popup, masquée d'elle-même sur "Tous" (qui ne masque jamais rien). Pour faire machine arrière, un bouton œil barré à côté de la barre de filtre bascule vers un panneau dédié listant uniquement les groupes/profils directement masqués dans le workspace actif (hiddenGroupsInWorkspace/hiddenProfilesInWorkspace, lues depuis rawGroupsSnapshot — un instantané non filtré conservé exprès pour ce panneau), chacun avec un bouton œil pour le réafficher. Popup à cases à cocher entièrement retirée.
  • La barre de filtre cherche partout, tout le temps (retour utilisateur, 2026-07-28) : onFilterChange() ignore désormais délibérément le filtrage de visibilité du workspace actif — un workspace ne doit contrôler que ce que l'arbre montre par défaut, jamais rendre quelque chose introuvable par la recherche.
  • Favoris cloisonnés par workspace, sans migration : les clés existantes sidebarPlus.favorites/favoriteGroups (déjà vivantes dans le config.yaml de l'utilisateur) sont réutilisées telles quelles comme favoris du workspace "Tous" ; chaque nouveau workspace a ses propres favorites/favoriteGroups sur son propre objet.
  • Ordre des dossiers/profils indépendant par workspace (retour utilisateur en test manuel, 2026-07-28 — revirement sur la décision initiale "ordre partagé"). Chaque SidebarWorkspace porte son propre groupOrder/profileOrder (même forme que le sidebarPlus.groupOrder top-level, qui reste le mécanisme du workspace "Tous" — zéro migration). Un dossier/profil pas encore réordonné dans un workspace donné retombe sur l'ordre de "Tous" (groupOrder top-level / weight natif) tant qu'on ne le déplace pas explicitement dans ce workspace. Réordonner en dehors de "Tous" n'écrit jamais le weight natif d'un profil — seulement workspace.profileOrder[groupId] — ce qui a un bénéfice de robustesse repéré par l'utilisateur en cours de route : si le plugin est un jour désinstallé, aucune donnée native (structure de groupes, poids de profils) n'a été touchée par les réorganisations faites hors "Tous", seul l'overlay sidebarPlus.workspaces devient orphelin dans config.yaml. Une liste d'ordre par workspace n'a besoin de décrire que les éléments visibles dans ce workspace (un élément masqué n'y est jamais rendu, sa position enregistrée n'a donc pas d'importance) — ce qui rend inutile le garde-fou anti-réorganisation initialement posé en v1 (bloquer le glisser-déposer quand des éléments masqués sont présents) : supprimé, plus de risque de corruption puisque chaque workspace a son propre ordre.
  • Workspace actif en localStorage (sidebarPlusActiveWorkspace), pas dans config.yaml — état par machine, changer d'onglet ne doit pas modifier un fichier synchronisé entre machines.
  • Sélecteur : implémenté en onglets horizontaux simples (flex-wrap, passent à la ligne s'il y en a beaucoup) + bouton "+". Le sélecteur adaptatif (bascule automatique en dropdown via ResizeObserver sous une largeur seuil) est différé — pas nécessaire tant que le nombre de workspaces reste faible en usage réel.
  • Couleurs contextuelles (bordure de terminal selon le workspace actif au lancement) : différé, non implémenté dans cette passe — touche le lancement de profil, jugé préférable comme étape revue séparément. Design inchangé : injection via clone en mémoire (structuredClone), jamais en mutant le profil d'origine (piège #12).
  • Le nom/icône/couleur d'un dossier ou son parent restent globaux, jamais spécifiques à un workspace (décision confirmée avec l'utilisateur le 2026-07-28) — cohérent avec le reste : un dossier a une seule identité et une seule position dans l'arborescence réelle ; seules sa visibilité et son ordre parmi ses frères sont cloisonnés par workspace.
  • Bug corrigé (2026-07-28) — réordonner un dossier via glisser-déposer était cassé, et déplacer un dossier vers un autre parent ("désimbriquer") pouvait orpheliner des sous-éléments : reparentGroup() recrée le dossier déplacé sous un nouvel id (piège #12, Tabby n'autorise pas de reparentage en place) puis migre profils/sous-dossiers avant de supprimer l'original. Le code migrait jusque-là depuis l'arbre affiché (dragged.children/.profiles) — donc filtré par le workspace actif : tout élément masqué dans ce workspace n'était jamais migré, restait rattaché à l'ancien id, puis se retrouvait orphelin quand l'original était supprimé. Corrigé pour migrer depuis un instantané complet et non filtré (allGroups, récupéré une fois via profilesService.getProfileGroups() puis transmis à travers la récursion). Deuxième volet du même bug : le changement d'id n'était répercuté nulle part — migrateWorkspaceGroupId() renomme désormais l'ancien id vers le nouveau dans hiddenGroupIds/groupOrder de tous les workspaces (pas seulement celui depuis lequel le déplacement a été fait) et dans le groupOrder top-level de "Tous". isSelfOrDescendant() (garde-fou anti-cycle) migré de la même façon de profileGroups vers rawGroupsSnapshot (non filtré), pour ne pas sous-détecter un cycle dont un maillon serait masqué dans le workspace actif.
  • Bug corrigé (2026-07-28) — imbriquer un dossier dans un autre était totalement impossible, et l'est resté à travers plusieurs correctifs successifs parce qu'il y avait trois causes indépendantes, chacune suffisante à elle seule. Diagnostiqué par pilotage automatisé du glisser-déposer via CDP (Input.dispatchMouseEvent + mesure de la géométrie en direct) sur des dossiers jetables grp-zzz-test-*, après que le test manuel eut échoué à départager les hypothèses. Détail complet dans les pièges #24, #25, #28 et #29 ; en résumé : (1) l'ordre de cdkDropListConnectedTo — CDK retient le premier conteneur qui matche et un ancêtre matche toujours, donc groups-root gagnait systématiquement ; (2) une règle CSS qui agrandissait les zones de dépôt pendant le glisser — reflow de tout l'arbre et rectangles déjà mis en cache par CDK ; (3) le placeholder de CDK à hauteur de ligne, qui en quittant sa position au-dessus de la cible faisait remonter celle-ci hors du curseur, d'où une oscillation infinie et l'asymétrie observée (glisser vers le haut fonctionnait, vers le bas jamais).
  • Geste de dépôt (2026-07-28) : moitié basse de la ligne d'un dossier = « déposer dedans », moitié haute = « réordonner à côté ». Obtenu sans ajouter d'espace mort — la liste d'enfants, quand elle est vide, est agrandie puis remontée par une marge négative de même valeur (contribution nette nulle au flux) et rendue transparente à la souris hors glisser (piège #26). L'espacement de l'arbre diminue au passage de 45px à 29px par dossier replié, à la demande de l'utilisateur. Un filet de sécurité complète le dispositif : rescueTargetGroupId() fait son propre test de collision sur la position réelle des lignes et rattrape les dépôts que CDK a résolus à tort sur la racine.
  • Surbrillance des zones de dépôt : retirée (demande utilisateur, 2026-07-28) — le placeholder de CDK, qui se déplace dans le dossier survolé, suffit comme retour visuel.
  • Icône par workspace : demandée par l'utilisateur, non implémentée (repoussée derrière les bugs de glisser-déposer, jamais reprise depuis). Design attendu : même picker que celui des profils/dossiers, ouvert par une entrée de menu contextuel sur l'onglet du workspace, icône affichée à côté du nom dans l'onglet. Implique un champ icon sur SidebarWorkspace.
  • Bug corrigé (2026-07-28) — un nouveau workspace pouvait sembler hériter de l'état d'un autre workspace : condition de course entre le rechargement déclenché par config.changed$ (sur chaque config.save(), y compris celui de la création) et l'appel explicite de selectWorkspace() juste après — deux loadTreeItems() concurrents, le dernier à se terminer (pas forcément le dernier démarré) l'emportait. Corrigé par un compteur de requête monotone (loadTreeRequestId) : chaque appel capture l'état du workspace actif avant son premier await (jamais relu après, pour ne pas hériter d'une mutation faite par un appel concurrent en cours de route), et seul l'appel le plus récemment démarré committe ses résultats dans this.profileGroups/ this.rootGroups à la fin.

Propositions issues du test manuel du 2026-07-29 📋 À arbitrer

Consignées à la demande de l'utilisateur pour vérification de faisabilité, aucune n'est implémentée.

  • Masquer par défaut dans les workspaces existants tout profil/dossier nouvellement créé (visible d'emblée uniquement dans « Tous »). Motif avancé par l'utilisateur : en l'état, chaque création apparaît d'un coup dans tous les workspaces, ce qui les « casse » systématiquement et impose un masquage manuel workspace par workspace. Inverse la décision d'origine (listes d'exclusion → visible par défaut partout), à ne pas confondre avec un simple réglage : le sens par défaut de l'appartenance change.
    Garantie nécessairement partielle

    Seules les créations passant par le plugin (createGroup(), pickProfileTemplate()) peuvent être interceptées. Un profil créé depuis les paramètres natifs de Tabby n'emprunte aucun de ces chemins et resterait visible partout — sauf à détecter les nouveautés au chargement (comparaison avec un instantané des ids connus), ce qui suppose de stocker cet instantané et de trancher le cas « profil vu pour la première fois sur une autre machine ».

  • Rendre configurable le comportement de la barre de filtre vis-à-vis des éléments masqués. Aujourd'hui le filtre cherche délibérément partout, y compris ce que le workspace actif masque (confirmé comme voulu par l'utilisateur au test du 2026-07-29) ; l'option offrirait le comportement inverse — restreindre la recherche au périmètre visible du workspace. Réglage sidebarPlus booléen, sans impact sur le stockage des workspaces.
  • Lever l'ambiguïté entre « réordonner » et « imbriquer » au glisser-déposer. Constat du test du 2026-07-29 : l'utilisateur pensait réordonner deux dossiers alors qu'il en imbriquait un dans l'autre. Ce n'est pas un défaut de cloisonnement — un re-parentage modifie l'arborescence réelle, donc tous les workspaces, ce qui est la conception actée — mais le geste ne se distingue que par quelques pixels (moitié haute d'une ligne = réordonner, moitié basse = déposer dedans, cf. piège #26). Pistes : retour visuel distinct selon la moitié survolée, seuil de déclenchement plus strict, ou modificateur clavier pour forcer l'imbrication.

Section "Sessions Actives" en haut de la sidebar

Zone pliable dédiée tout en haut de la barre latérale, listant uniquement les connexions SSH ouvertes en arrière-plan.

  • Fonctionnalités : intégration visuelle des états de transfert SFTP actifs (vitesse, file d'attente).
  • Interaction : le clic sur une session active déplace instantanément le focus sur l'onglet ou le split pane correspondant.
Note d'architecture

Bien que SCP ait été évoqué, le socle de Tabby (tabby-ssh) exporte déjà SFTPSession (voir point de veille AI-CONTEXT), il est donc impératif de s'appuyer sur SFTP pour garantir la stabilité globale.

Phase 2 — productivité

Sélection multiple

Uniquement pour les profils, pas les groupes. Permet de sélectionner plusieurs profils puis de les déplacer tous ensemble vers un autre groupe en un seul geste.

  • Mécanisme retenu : sélection éphémère par cases à cocher (Shift/Ctrl+clic pour étendre), puis clic droit sur le dossier cible → "Déplacer la sélection ici" — plutôt que le multi-drag natif Angular CDK (qui ne gère pas nativement le déplacement simultané de plusieurs éléments et aurait demandé d'adapter onProfileDrop/l'aperçu de drag pour un cas jugé trop complexe/fragile).
  • Comportements calqués sur les standards OS : un clic gauche simple sans touche modificatrice réinitialise la sélection en cours ; un clic droit en dehors de la sélection l'annule et ouvre directement le menu contextuel standard (création/édition/ suppression) plutôt que le menu de déplacement.

Tunnels SSH

Conçu comme une surcouche visuelle branchée directement sur le moteur de port-forwarding déjà natif de Tabby — pas de réimplémentation du tunneling lui-même. Le plugin se contente d'exposer la création/config en un clic depuis le menu contextuel d'un profil (plutôt que via la fenêtre de gestion des tunnels native, jugée plus lourde et déconnectée des profils), et de refléter l'état des tunnels déjà gérés par Tabby.

  • Indicateur visuel (pastille façon "maillon de chaîne") sur le profil concerné quand un tunnel l'utilisant comme passerelle est actif.
  • Panneau des tunnels actifs en bas de sidebar.
  • Si Tabby gère déjà la reprise sur micro-coupure réseau nativement, le plugin n'a qu'à en afficher l'état plutôt qu'à réimplémenter l'auto-reconnexion.

Ouverture groupée d'un dossier ("Group Exec")

Clic droit sur un dossier → "Ouvrir tout" : lance une session pour chaque profil du dossier, en onglets séparés ou en split panes. Intérêt renforcé si couplé à la saisie synchronisée déjà native de Tabby (multi-input) pour exécuter la même commande sur plusieurs serveurs en parallèle. Priorité basse — pas demandée en premier par l'utilisateur.

Détection et validation des sessions interactives (Auto-Enter)

Automatisation du login en simulant l'appui sur "Entrée" dès qu'une invite interactive (login/password) est détectée. Si le mot de passe est pré-rempli, cela valide ; s'il est vide, cela passe l'invite.

  • Implémentation UI : l'option ne doit PAS être globale. Un commutateur (toggle) "Activer l'Auto-Enter" doit être visible dans l'interface de configuration du profil, positionné directement à côté ou juste en dessous du champ natif de mot de passe enregistré.
Alerte de fragilité technique

L'injection de ce toggle près du champ mot de passe implique d'intervenir sur le DOM de la modale native EditProfileModalComponent. Cette zone étant critique et instable (voir piège #17 et le point fragile associé dans AI-CONTEXT.html), le hook d'injection Angular/DOM devra intégrer un mécanisme de repli (fallback) strict. Si le DOM de Tabby change lors d'une mise à jour de l'application, le toggle doit se déporter gracieusement dans le menu contextuel du profil ("Options Sidebar" → "Auto-Enter") ou dans les options globales, sans provoquer de plantage de l'interface.

Clone Express de profil

Clic droit sur un profil → action "Dupliquer le profil". Génère instantanément une copie parfaite du profil sous le même groupe (avec suffixe " - Copie").

Contrainte technique : pour éviter toute corruption ou pollution de config.yaml (piège #12), la duplication doit s'exécuter via un structuredClone() profond en mémoire de l'objet profil avant l'appel à l'API de persistance de Tabby.

Historique des Profils Récents

Liste dynamique et pliable affichant les 5 derniers profils de connexion utilisés, positionnée juste en dessous de la zone des sessions actives pour un réengagement ultra-rapide sans navigation dans l'arborescence.

Quick Snippets (Macros de Sidebar)

Permet d'associer des commandes textuelles récurrentes (ex. redémarrage de service, consultation de logs) à un profil ou un groupe.

  • Interaction : un clic droit sur l'élément dans la sidebar déploie un sous-menu listant ces macros personnalisées. Cliquer sur une macro l'envoie et l'exécute instantanément dans le terminal actif de la session correspondante, évitant les allers-retours avec un gestionnaire externe.

Favoris d'icônes (distincts des « Récentes »)

Demandé directement par l'utilisateur (2026-07-28) après usage du picker d'icônes existant. Bouton étoile sur chaque icône affichée dans le picker (grille "Récentes", grille de résultats de recherche, SVG personnalisé une fois appliqué) pour l'épingler dans une liste séparée et permanente, indépendante de la fréquence d'usage — contrairement à « Récentes » qui s'use avec le temps (une icône peu utilisée finit par en sortir), une icône favorite reste tant qu'on ne la retire pas explicitement.

  • Nouvelle clé sidebarPlus.favoriteIcons: string[], même format que recentIcons (classe FontAwesome/Iconify ou SVG brut déjà sanitisé) — à déclarer dans les defaults de SidebarPlusConfigProvider dès l'implémentation (piège #16, sinon la liste ne survit pas à un redémarrage).
  • Nouvelle section « Favoris » dans le picker, positionnée au-dessus de « Récentes », visible même sans recherche active (même emplacement/logique d'affichage que la section "Récentes" actuelle).
  • Le bouton étoile doit être disponible sur chaque tuile du picker, pas seulement au moment de la sélection — l'utilisateur doit pouvoir épingler une icône déjà présente dans "Récentes" ou dans les résultats de recherche sans avoir à la ré-appliquer.

Lié, déjà fait le 2026-07-28 (voir AI-HISTORY.html) : le nombre d'icônes "Récentes" affichées est passé de 5 à 20 (MAX_RECENT_ICONS), pour garder les icônes fréquentes à portée de main même avant d'implémenter ce chantier des favoris.

Non daté — à faire quand utile

Options & polissage UI

Agencement de la page de paramètres (Settings Layout)

Structurer l'interface de configuration du plugin en 4 sections distinctes :

  1. Général & Affichage : options de masquage de l'UI native redondante, gestion des raccourcis clavier globaux.
  2. Sessions Actives & SFTP : fréquences de rafraîchissement, interrupteur de gel de la vue, historique de file d'attente.
  3. Workspaces : liste des espaces de travail, import/export JSON sélectif, assignation des couleurs de bordure par défaut.
  4. Automatisation & Macros : gestion globale des Quick Snippets et logs du moteur d'Auto-Enter.
  • Double entrée de configuration : sous-onglet dédié dans les options globales de Tabby (tabby-settings) + icône d'engrenage discrète en bas à droite de la sidebar, les deux pointant vers les mêmes réglages.
  • UI trimming : option pour masquer des composants natifs de Tabby devenus redondants (ex. bouton de transfert SFTP d'origine) via injection de CSS global (display: none !important), en s'inspirant des patterns déjà observés dans tabby-sftp-plus.
  • Raccourcis globaux : HotkeyProvider pour mapper des raccourcis clavier (changer de workspace, basculer vers le SFTP actif, afficher le panneau des tunnels).

Barre de filtrage rapide (Sidebar Search)

Micro-champ de recherche textuelle épinglé en haut de la liste pour filtrer instantanément les profils et groupes affichés sans changer de workspace. Focus via le raccourci Ctrl+F ou Cmd+F lorsque la sidebar est active.

Partage rapide de groupe (Presse-papiers)

Clic droit sur un dossier/groupe → "Copier la structure (JSON)". Extrait l'arborescence complète au format JSON en purgeant obligatoirement tous les secrets, identifiants et mots de passe. L'action symétrique "Coller le groupe" à la racine de la sidebar permet d'importer instantanément la structure.

Notes de profil (Mémento contextuel)

Zone de texte légère ou bulle d'aide éditable propre à chaque profil pour y consigner des notes d'exploitation (commandes de relance, rappels de maintenance, numéros de tickets).

Indicateur de santé (Ping live)

Option pour afficher une micro-pastille colorée (vert/orange/rouge) à côté des sessions actives représentant la latence réseau actuelle via un ping régulier en tâche de fond (désactivable).

Robustesse — édition de profil

Envelopper la séquence clickNativeProfileRow() (édition de profil par clic droit — le point le plus fragile du plugin, voir AI-CONTEXT §3.1) dans un bloc try/catch verbeux, pour qu'un futur changement de DOM dans tabby-settings affiche un message clair ("Impossible d'ouvrir automatiquement la modale d'édition, redirection vers Paramètres → Profils") plutôt que d'échouer silencieusement.

Hors périmètre

Vault Auto-Unlock — plugin séparé tabby-better-vault

Décision actée

Le déverrouillage automatique du coffre-fort Tabby (éviter de ressaisir le mot de passe maître à chaque démarrage) ne fait pas partie de better-sidebar — ce n'est pas une fonctionnalité de sidebar, et c'est le point le plus sensible (manipulation d'un secret utilisateur) envisagé sur cet écosystème de plugins. Devient un plugin indépendant, tabby-better-vault, publié et versionné séparément — dossier de travail et gouvernance propres créés le 2026-07-26 : .AIRules de tabby-better-vault (lien relatif valable tant que les deux dossiers restent côte à côte dans Développement/). Design détaillé ci-dessous transporté à l'identique là-bas.

  • Interfaçage entre plugins indépendants : possible, pattern identifié. Tous les plugins Tabby tournent dans le même process Electron et partagent le même injecteur Angular — déjà le mécanisme utilisé par better-sidebar pour consommer des classes de tabby-core/tabby-settings/tabby-ssh. Un futur tabby-better-vault exporterait un service minimal (ex. VaultBridgeService), et better-sidebar l'importerait en dépendance optionnelle avec @Optional()/Injector.get(TOKEN, null) — la section correspondante des réglages disparaît simplement si le plugin Vault n'est pas installé. Pattern non officiel (effet de bord du chargeur de plugins, pas une API documentée) : le contrat entre les deux packages serait à notre charge (versioning à gérer). Même discipline de vérification que le reste du projet : si tabby-better-vault exporte un service, vérifier les DEUX niveaux (typings ET bundle dist/index.js compilé) avant de s'y fier — voir piège #13 d'AI-CONTEXT.html.
  • Design prévu pour ce futur plugin : délégation à l'OS via electron.safeStorage (Windows : Gestionnaire d'identifiants/DPAPI ; macOS : Trousseau d'accès/Keychain avec Touch ID si activé ; Linux : Secret Service API/libsecret via GNOME Keyring/KWallet). Mécanisme opt-in, injection programmatique du mot de passe déchiffré dans le VaultService de Tabby avant que la pop-up native de saisie n'apparaisse.
  • Sécurité RAM : la variable JS contenant le mot de passe maître déchiffré en clair doit être immédiatement écrasée (= null) dès que l'injection dans le moteur de Tabby est validée, pour limiter au minimum la fenêtre d'exposition du secret en mémoire vive.
  • Garde-fou : si l'injection échoue (ex. mot de passe maître changé depuis les réglages natifs de Tabby), suppression immédiate du token local obsolète et retour transparent à la pop-up native.
  • Point à vérifier avant tout début de code : confirmer que VaultService (ou l'équivalent réel dans le tabby-core installé) expose bien une méthode d'injection programmatique utilisable depuis un plugin tiers — typings ET bundle compilé, ne jamais conclure sur un seul des deux (piège #13).
