Dernière revue : 2026-07-26

Faits stables sur l'architecture de ce plugin, pièges déjà résolus (à ne pas refaire) et décisions de design déjà actées pour les fonctionnalités pas encore construites. Les commandes de build/dev restent dans CLAUDE.md à la racine du dépôt — ce fichier ne les duplique pas.

1. Identité du projet

  • Dossier local historique : tabby-ssh-sidebar (jamais renommé, casserait la jonction NTFS de dev). Nom réel du package npm / dépôt GitHub : tabby-better-sidebar. Le loader de plugins Tabby se base sur le nom du dossier dans plugins/node_modules/ (déjà correct), pas sur package.json.name ni le nom du dossier source — incohérence cosmétique sans impact fonctionnel.
  • LICENSE garde encore le placeholder "tabby-sidebar-plus contributors" — à corriger avant une release soignée.
  • Identité Git configurée localement à ce dépôt uniquement (pas --global) : TooMuhtsh <188712716+TooMuhtsh@users.noreply.github.com> (email noreply GitHub du compte perso). À reconfigurer manuellement sur toute nouvelle machine (non inclus dans ce qui est poussé sur GitHub).

2. Pièges rencontrés (référence numérotée — ne pas renuméroter)

Chaque piège est référencé ailleurs par son numéro (CLAUDE.md, journal). Ne jamais réordonner cette liste.

#1 — TABBY_PLUGINS cassé sur Windows

Tabby fait process.env.TABBY_PLUGINS.split(':') ; un chemin Windows (C:\...) contient un : après la lettre de lecteur → chemin tronqué, plugin jamais trouvé, sans erreur visible. Bug Tabby, pas du plugin. Solution retenue : ne pas utiliser cette variable. Jonction NTFS directe :

New-Item -ItemType Junction -Path "$env:APPDATA\tabby\plugins\node_modules\tabby-better-sidebar" -Target "C:\Users\Alex Ramirez\Documents\Développement\tabby-ssh-sidebar"
Piège opérationnel

Désactiver le plugin depuis l'UI Extensions de Tabby supprime la jonction (pas juste un flag) — la recréer manuellement pour revenir en mode dev.

#2 — package.json sans champ author

Le loader de plugins fait author.name || author sans vérifier l'existence — plante silencieusement, logué juste comme "Cannot load package info for X". Toujours mettre un champ author, même vide.

#3 — templateUrl/styleUrls ne marchent pas pour un plugin tiers

Résolus uniquement au bootstrap principal de l'appli. Pattern correct (voir tabby-clippy) :

@Component({ template: require('./x.pug') })  // pas templateUrl

SCSS : import en side-effect (import './x.scss') + style-loader/ css-loader/sass-loader en webpack (injection CSS globale). Nécessite apply-loader devant pug-loader pour que require('./x.pug') retourne une string.

#4 — Versions verrouillées pour Angular 15 (peer dep de tabby-core)

  • typescript@^4.9.x (pas 5.x)
  • pug@^2.0.x (pug-loader@2.4.0 exige pug@^2.0.0)
  • @types/node@^18.19.0 (26.x embarque des typings node:ffi qui ne parsent pas sous TS 4.9)
  • @ng-bootstrap/ng-bootstrap@^14.x (la dernière vise Angular 18+)

#5 — npm install échoue sur tabby-ssh

Son postinstall tente de compiler des bindings natifs inutilisés (on ne consomme que ses types). → npm install --ignore-scripts.

#6 — Typings npm de tabby-core en retard sur l'app installée

buildGroupTree(), icon/color/parentGroupId sur ProfileGroup existent à l'exécution (1.0.235) mais pas dans les types publiés (tag nightly, plus vieux). → Augmentation de type dédiée (src/tabby-core-augment.d.ts) plutôt que des any disséminés.

#7 — La sidebar native existe déjà, cachée

Paramètres → Window → "Show profile sidebar" (config.store.showProfileTree, composant profile-tree). Utile pour comparer un comportement suspect avec le natif.

#8 — Debug via Chrome DevTools Protocol

Tabby.exe --debug --remote-debugging-port=9333 → connexion Node en WebSocket natif pour lire la vraie console et interroger le DOM. Utile car Tabby avale beaucoup d'erreurs de chargement de plugin dans des catch génériques.

Important

Après toute modification du plugin : tuer et relancer tout le process Tabby.exe — pas un simple reload de page. Le cache de modules Node est global au process.

#9 — gh auth login authentifie le compte actif du navigateur

Pas un compte choisi dans le CLI. Vérifier le compte actif dans le navigateur avant, ou gh auth status --active après.

#10 — Auteur des commits ≠ compte GitHub utilisé

Indépendants : git config user.email détermine l'auteur affiché, le compte GitHub authentifié détermine qui pousse. Email noreply officiel pour committer "en tant que" un compte perso : {id}+{login}@users.noreply.github.com (id via gh api user --jq '{id, login}').

#11 — git filter-branch bloqué par le mode auto de Claude Code

Réécriture d'historique jugée sensible même sur un repo perso sans collaborateurs. L'utilisateur doit lancer la commande lui-même via le préfixe ! (hors sandbox classifié). Nécessite git push --force après (les hash changent).

#12 — getProfileGroups() ne clone pas profondément — pollue config.yaml

Critique — cause racine, ne jamais réintroduire

A réellement corrompu la configuration de production de l'utilisateur une fois (groupes orphelins, entrées dupliquées) lors d'un test de re-parentage.

profilesService.getProfileGroups() peut renvoyer des références directes vers config.store.groups (contrairement à getProfiles({clone:true}), qui clone bien). buildGroupTree() attache alors un .children calculé directement sur ces objets vivants ; au config.save() suivant (n'importe lequel, favoris compris), cette propriété polluante est sérialisée → groupes dupliqués/orphelins dans config.yaml.

Fix retenu : structuredClone() sur groups juste après getProfileGroups(), avant toute manipulation. Le plugin ne mute jamais que sa propre copie.

Corollaire : profilesService.writeProfileGroup(group) fait une recherche plate, racine uniquement (config.store.groups.find(...)) — fondamentalement inadaptée pour déplacer un groupe entre children: imbriqués (silencieux en cas d'échec). Le re-parentage passe donc par recréation (newProfileGroup) + migration des profils un par un (writeProfile) + suppression de l'ancien (deleteProfileGroup) — jamais par réassignation directe de parentGroupId.

Discipline de méthode qui en découle : toute nouvelle fonctionnalité touchant groupes/profils doit être testée d'abord sur des entrées jetables (grp-zzz-test-*), jamais directement sur les vraies données.

#13 — @hidden ne veut pas dire "non exporté"

Les deux sont indépendants. EditProfileModalComponent est @hidden ET absente du bundle réel (inutilisable) ; SettingsTabComponent est elle aussi @hidden mais bel et bien exportée (typings et bundle). @hidden n'exclut que de la doc générée. → Toujours vérifier les deux niveaux : typings/index.d.ts ET le bloc __webpack_require__.d(...) de dist/index.js compilé.

#14 — :host ne fonctionne pas dans le SCSS de ce plugin

Le SCSS est injecté en CSS globale brute (side-effect import, voir piège #3) — :host n'est interprété que par le compilateur de templates Angular ou en Shadow DOM natif, ni l'un ni l'autre ne s'applique ici. Le navigateur ignore silencieusement la règle (aucune erreur). → Cibler le nom du tag custom element réel (ex. sidebar-plus-tree { ... }) à la place.

#15 — @HostListener('document:click') ignore stopPropagation()

Se déclenche même quand un descendant a appelé $event.stopPropagation() sur un (click) normal. → Ne jamais compter sur la propagation ; vérifier explicitement (event.target as HTMLElement).closest('.mon-popup, ...') dans le handler lui-même.

#16 — ConfigProvider.defaults doit déclarer chaque clé individuellement

Une clé sous config.store.sidebarPlus non déclarée dans les defaults mute très bien en mémoire mais ne persiste jamais dans config.yaml — silencieux, aucune erreur. Touché recentIcons et groupOrder (ce dernier croyait fonctionner depuis le début). → Toute nouvelle clé sidebarPlus.X doit être ajoutée aux defaults de SidebarPlusConfigProvider (src/configProvider.ts), même vide.

#17 — EditProfileModalComponent : cumul des pièges #13 et #6

Exportée par le bundle réel mais absente des typings npm (TS2614 à la compilation si import direct). Pire : le champ s'appelle partialProfile à l'exécution alors que les typings npm obsolètes le nomment profile — utiliser ce dernier compilerait sans erreur mais ferait planter silencieusement la modale. → Augmentation de type dédiée (src/tabby-settings-augment.d.ts) avec les vrais noms de champs, vérifiés directement dans le bundle compilé (jamais seulement les typings ni le .ts source de l'app).

#18 — Handler (contextmenu) sur l'espace vide de la sidebar

Doit être posé sur l'élément qui remplit réellement tout l'espace visible (.sidebar-plus-tree.h-100), pas sur celui qui ne fait que la hauteur de son contenu (.sidebar-plus-tree-container) — sinon un clic droit sous le dernier groupe ne déclenche rien pour un vrai clic utilisateur (un clic synthétique de test peut donner une fausse impression que ça marche).

#19 — cdkDropList vide = 0px de hauteur

Cible de drop quasi impossible à atteindre. Devenu un bug de production réel avec "Nouveau dossier..." (toujours vide à la création) : le drop échoue silencieusement, aucune erreur, aucun changement dans config.yaml. → min-height: 8px sur tous les div[id^='profiles-'] et div[id^='groups-'].

#20 — Classement npm search très bas pour un paquet neuf

Constaté quelques heures après la publication de tabby-better-sidebar@0.2.0 : le paquet est bien indexé (présent dans les résultats du mot-clé tabby-plugin), mais même une recherche par nom exact ne le fait pas apparaître dans les 250 premiers résultats de registry.npmjs.org/-/v1/search — l'algorithme pondère fortement la popularité (téléchargements, maintenance), qu'un paquet neuf n'a pas encore. Pas un bug de publication. Devrait s'améliorer avec l'usage, sans garantie de délai. Contournement pour tester l'install "officielle" en attendant :

cd "$env:APPDATA\tabby\plugins"
npm install tabby-better-sidebar

3. Points fragiles à revérifier après une mise à jour de Tabby

Ce plugin s'appuie par endroits sur des classes/composants internes non garantis par une API publique stable. Rien ne casse souvent, mais une mise à jour majeure de Tabby peut le faire silencieusement (pas d'erreur de compilation, juste un comportement qui ne fait plus rien ou fait la mauvaise chose). Tester chaque point après toute mise à jour de Tabby :

1. Édition de profil (clic droit → "Éditer...") — le plus fragile

Pilote du DOM interne non versionné de tabby-settings : chaque ligne est un .collapse-item, cliquer dessus ouvre directement la modale (pas de bouton dédié) ; .modal-content/.modal-header h3/.modal-footer button pour détecter la fermeture. Si ça casse : la modale ne s'ouvre plus, ou pire une mauvaise ligne s'ouvre. Pas destructeur si seule la détection de fermeture casse (l'utilisateur ferme l'onglet à la main).

2. SettingsTabComponent.activeTab

Vrai @Input() documenté mais toujours @hidden donc non contractuel. Vérifier que activeTab: 'profiles' amène toujours sur le bon sous-onglet.

3. SFTPPanelComponent/SFTPSession/SFTPFile

Prévus pour le panneau SFTP (pas encore implémenté) — vérifier qu'ils restent exportés par tabby-ssh et que SFTPPanelComponent.session attend toujours une SSHSession déjà connectée.

4. writeProfileGroup()/newProfileGroup()/deleteProfileGroup()

Utilisées uniquement selon la discipline du piège #12. Si le format de stockage des groupes dans config.yaml change, retester le re-parentage sur des groupes jetables avant de faire confiance au comportement existant.

5. Clone non garanti de getProfileGroups()/buildGroupTree()

Le structuredClone() défensif (piège #12) part du principe que l'API peut renvoyer des références vivantes. Si une future version clone proprement en interne, il devient superflu mais reste inoffensif à garder par précaution.

6. profile-tree toujours non exporté

Vérifier périodiquement (montée majeure de tabby-core) s'il a fini par être exporté — simplifierait la maintenance en permettant de réutiliser le composant natif au lieu de la copie locale.

7. EditProfileModalComponent (utilisé pour "Nouveau profil...")

Augmentée manuellement avec les noms de champs réels (piège #17). Si une future version de Tabby renomme ces champs, l'erreur sera silencieuse à la compilation (l'augmentation "ment" à TypeScript) — seul un test manuel de "Nouveau profil..." révélera le problème.

4. Décisions de design actées pour les fonctionnalités pas encore construites

Détail de chantier dans ROADMAP.html — ici seulement les choix déjà tranchés à respecter au moment de l'implémentation.

SFTP contextuel

  • Espace de la sidebar elle-même (bascule Profils/SFTP), pas un panneau séparé ancré à droite. Volet fichiers locaux masqué par défaut. Déclenché depuis un onglet SSH déjà connecté (pas de session headless dédiée).
  • SFTPPanelComponent/SFTPSession/SFTPFile confirmés exportés par tabby-ssh — pas de réimplémentation locale nécessaire.
  • Vue liée au SplitTabComponent actif (bascule au changement de focus, avec option de gel) ; état "en attente d'une session SSH" si l'onglet actif n'en a pas.
  • Dernier chemin distant visité mémorisé par onglet (en mémoire, pas persistant).
  • Liste de fichiers chargée par blocs (lazy loading RxJS) pour éviter de figer le thread Electron.
  • Suivi des transferts : flèches d'activité ↑/↓ à côté du profil + pourcentage au survol (tooltip), pas de barre de progression classique (coût de re-render Angular trop élevé avec plusieurs transferts en parallèle). Mini-gestionnaire pliable en bas de sidebar pour l'historique/la file d'attente.

Workspaces

  • Stockage dans config.yaml via ConfigProvider (pas de fichiers JSON externes séparés) — l'objectif de portabilité est déjà couvert nativement puisque config.yaml contient tout en un seul fichier synchronisable tel quel. Export/import JSON ponctuel prévu pour le partage sélectif (structure d'un workspace sans les secrets), pas comme source de vérité vivante.
  • Favoris cloisonnés par workspace (un profil peut être favori dans A mais pas B). L'ordre des profils/groupes reste, lui, partagé entre tous les workspaces.
  • Workspace "Tous" permanent par défaut (affichage non filtré).
  • Logique de cascade au masquage d'un dossier parent : popup proposant "ce workspace seulement" vs "tous les workspaces".
  • Couleurs contextuelles par workspace : injectées via structuredClone au double-clic de lancement, jamais en mutant le profil d'origine (cohérent avec piège #12).
  • Sélecteur : onglets horizontaux par défaut, bascule automatique vers un dropdown pilotée par un ResizeObserver sur la largeur réelle de la sidebar (pas un seuil fixe sur le nombre de workspaces).

Sélection multiple

Mécanisme retenu : cases à cocher (Shift/Ctrl+clic pour étendre) + clic droit sur le dossier cible → "Déplacer la sélection ici" — plutôt que le multi-drag natif Angular CDK (jugé trop complexe/fragile). Comportements calqués sur les standards OS : un clic gauche simple sans modificateur réinitialise la sélection ; un clic droit hors sélection l'annule et ouvre le menu contextuel standard. Uniquement pour les profils, pas les groupes.

Tunnels SSH

Surcouche visuelle sur le moteur de port-forwarding déjà natif de Tabby (pas de réimplémentation) : création/config en un clic depuis le menu contextuel d'un profil, indicateur visuel (pastille) sur le profil concerné, panneau des tunnels actifs en bas de sidebar.

Ouverture groupée d'un dossier ("Group Exec")

Clic droit sur un dossier → "Ouvrir tout" : lance une session par profil du dossier, à coupler idéalement avec la saisie synchronisée déjà native de Tabby.

Vault Auto-Unlock — hors périmètre, plugin séparé

Décision actée

Le déverrouillage automatique du coffre-fort Tabby ne fait pas partie de better-sidebar — ce n'est pas une fonctionnalité de sidebar, et c'est le point le plus sensible (manipulation d'un secret utilisateur) envisagé sur ce projet. Deviendrait un plugin séparé, ex. tabby-vault-unlock.

  • Interfaçage entre plugins indépendants : possible via l'injecteur Angular partagé (tous les plugins Tabby tournent dans le même process). tabby-vault-unlock exporterait un service minimal, better-sidebar l'importerait en dépendance optionnelle avec @Optional()/Injector.get(TOKEN, null) — pas d'erreur si le plugin Vault n'est pas installé. Pattern non officiel (effet de bord du chargeur de plugins, pas une API documentée) : le contrat entre les deux packages est à notre charge.
  • Design prévu pour ce futur plugin : délégation à l'OS via electron.safeStorage (DPAPI/Keychain/libsecret selon l'OS), opt-in, injection dans le VaultService de Tabby avant la pop-up native. La variable JS contenant le mot de passe déchiffré en clair doit être immédiatement écrasée (= null) dès l'injection validée. Garde-fou si l'injection échoue : suppression du token local obsolète, retour à la pop-up native.
  • À vérifier avant tout code : que VaultService expose une méthode d'injection programmatique utilisable depuis un plugin tiers (typings ET bundle compilé, piège #13).

Options & polissage UI

  • Double entrée de configuration : sous-onglet dans tabby-settings + icône d'engrenage dans la sidebar, mêmes réglages.
  • UI trimming : masquer des composants natifs redondants via CSS global (display: none !important), inspiré de tabby-sftp-plus.
  • Raccourcis globaux via HotkeyProvider (changer de workspace, basculer SFTP, afficher les tunnels).

Explicitement écarté

Importateur de sessions MobaXterm (.mxtpro/.ini) — non prioritaire, des outils de conversion existent déjà. À reconsidérer seulement si ce point de friction remonte concrètement.
